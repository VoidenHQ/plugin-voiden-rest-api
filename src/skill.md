## Extension: Voiden REST API

Provides HTTP request/response block types. All blocks live inside or alongside a `request` container.

> **Singleton per section:** `request`, `headers-table`, `query-table`, `path-table`, `url-table`, `multipart-table`, `cookies-table`, and `options-table` are each allowed at most once per section — edit the existing block instead of inserting a second one. `json_body`, `xml_body`, and `yml_body` are each independently singleton (checked only against themselves). Full cross-plugin table: base voiden skill → "Singleton Blocks — One Per Section".

### request — Request Container

Always required. Wraps all other blocks for a single HTTP call.

```yaml
---
type: request
attrs:
  uid: "05119029-b827-45fe-a2cc-55a5f0ba6609"
content:
  - type: method
    attrs:
      uid: "35d05fd6-1e12-4f6a-97d5-5c66d59bc61f"
      method: POST
      visible: true
    content: POST
  - type: url
    attrs:
      uid: "f84b83da-7fe7-415f-baa1-b045adfd7438"
    content: https://api.example.com/users
---
```

### method — HTTP Method

```yaml
- type: method
  attrs:
    uid: "uid"
    method: GET        # GET POST PUT PATCH DELETE HEAD OPTIONS
    visible: true
  content: GET
```

### url — Endpoint URL

```yaml
- type: url
  attrs:
    uid: "uid"
  content: https://api.example.com/users/{{USER_ID}}
```

### Key/Value/Description Tables — headers-table, query-table, path-table, multipart-table, url-table, options-table

These six table types now default to **3 columns — Key, Value, Description** (Description added; `cookies-table` below is intentionally excluded and stays 2-column). Two rules:

1. **New tables**: give every row all 3 elements — `["key", "value", "description"]` (use `""` for description if there's nothing to say) — matching what the app's own UI produces when you insert one of these blocks today. A table where every row is uniformly 2 elements still opens fine (existing files aren't broken, no migration needed), but don't *author* fresh 2-element rows going forward.
2. **Adding a row to an *existing* table**: match that table's own current row length, not this doc's default. The table header (and whether a Description column shows at all) is derived only from the **first row's** cell count — every other row is expected to match it. A table with some 2-element rows and some 3-element rows (e.g. an old 2-column table that gets one new 3-element row appended) is genuinely inconsistent and breaks rendering/editing, unlike a uniformly-old table, which is fine. Read the existing rows first; match their length exactly.

### headers-table — HTTP Headers

```yaml
---
type: headers-table
attrs:
  uid: "uid"
content:
  - type: table
    rows:
      - attrs: { disabled: false }
        row: [Content-Type, application/json, ""]
      - attrs: { disabled: false }
        row: [Authorization, "Bearer {{API_TOKEN}}", "Auth token from the login response"]
      - attrs: { disabled: true }
        row: [X-Debug, "true", "Only needed against the staging API"]
---
```

Row format: `[header-name, header-value, description]`. Set `disabled: true` to skip a row.

### query-table — Query Parameters

```yaml
---
type: query-table
attrs:
  uid: "uid"
content:
  - type: table
    rows:
      - attrs: { disabled: false }
        row: [page, "1", ""]
      - attrs: { disabled: false }
        row: [limit, "20", "Max 100 per the API docs"]
      - attrs: { disabled: true }
        row: [sort, desc, ""]
---
```

### path-table — Path Parameters

For URLs with `{id}` or `:id` segments:

```yaml
---
type: path-table
attrs:
  uid: "uid"
content:
  - type: table
    rows:
      - attrs: { disabled: false }
        row: [id, "{{USER_ID}}", ""]
---
```

### json_body — JSON Request Body

```yaml
---
type: json_body
attrs:
  uid: "uid"
  body: |
    {
      "name": "John Doe",
      "email": "john@example.com",
      "role": "user"
    }
---
```

### xml_body — XML Request Body

```yaml
---
type: xml_body
attrs:
  uid: "uid"
  body: |
    <user>
      <name>John Doe</name>
      <email>john@example.com</email>
    </user>
---
```

### yml_body — YAML Request Body

```yaml
---
type: yml_body
attrs:
  uid: "uid"
  body: |
    name: John Doe
    email: john@example.com
---
```

### multipart-table — Multipart Form Data

```yaml
---
type: multipart-table
attrs:
  uid: "uid"
content:
  - type: table
    rows:
      - attrs: { disabled: false }
        row: [name, "John Doe", ""]
      - attrs: { disabled: false }
        row: [role, "admin", "Must be one of: admin, member, viewer"]
---
```

Row format for text fields: `[field-name, value, description]` — 3-element array (see "Key/Value/Description Tables" above). File upload rows use a nested `fileLink` node structure generated by the Voiden UI file picker; do not hand-craft file rows.

### cookies-table — Request Cookies

```yaml
---
type: cookies-table
attrs:
  uid: "uid"
content:
  - type: table
    rows:
      - attrs: { disabled: false }
        row: [session_id, "{{SESSION_ID}}"]
      - attrs: { disabled: false }
        row: [tracking, "abc123"]
---
```

Row format: `[cookie-name, cookie-value]`. Set `disabled: true` to skip a row.

### options-table — Request Options

```yaml
---
type: options-table
attrs:
  uid: "uid"
content:
  - type: table
    rows:
      - attrs: { disabled: false }
        row: [follow_redirects, "true", ""]
---
```

Row format: `[option-name, option-value, description]` — 3-element array. Supported options:

| Option | Values | Description |
|--------|--------|-------------|
| `follow_redirects` | `true` / `false` | Whether to follow HTTP redirects (default `true`) |

### url-table — URL-Encoded Form Data

```yaml
---
type: url-table
attrs:
  uid: "uid"
content:
  - type: table
    rows:
      - attrs: { disabled: false }
        row: [username, john_doe, ""]
      - attrs: { disabled: false }
        row: [password, "{{PASSWORD}}", ""]
---
```

## response — Recorded Execution Result

A `response` block is a **read-only historical record** of a request's last real execution — written automatically by the `voiden-mcp-server` MCP tools (`write_result`) or the `voiden-runner` CLI, placed immediately after the `request` block it belongs to (preceded by a `## Response recorded` heading). **Never author one by hand** — it's a record of what actually happened, not something to write speculatively.

```yaml
---
type: response
attrs:
  uid: "9635349b-26bb-4f43-84ac-5d438e970507"
  requestUid: "ef290a0f-b183-47b1-9c57-c6510708973d"
  capturedAt: "2026-07-24T07:00:46.258Z"
  success: true
  status: 200
  statusText: OK
  durationMs: 1128.99
  size: 525
  requestHeaders:
    Content-Type: application/json
  requestBody: |
    { "message": "Hello from Voiden!" }
  responseHeaders:
    content-type: application/json; charset=utf-8
  body: '{"headers":{...},"body":{...}}'
---
```

| Attr | Description |
|------|-------------|
| `requestUid` | The `uid` of the `request` block this result belongs to — how it's matched back on re-run |
| `success` / `status` / `statusText` | Outcome of the call |
| `durationMs` / `size` | Timing and response size |
| `requestHeaders` / `requestBody` | What was actually sent |
| `responseHeaders` / `body` | What came back (`body` may be truncated with `truncated: true` if large) |
| `error` | Present only if the request failed before a response was received |

Re-running the request replaces the existing `response` block for that `requestUid` in place — it doesn't accumulate duplicates.
